# ProVDesk CI — Windows x64

[Français](README.md)

Complete Windows client build from **the Bitbucket checkout commit**, signed
through the **WanPulse framework**. A push to `master` automatically builds, signs,
publishes a GitHub release, then publishes the final EXE to the product share.
The same step is available manually as `provdesk-build-sign-package` on any branch.
Only `master` publishes; other branches retain signed Bitbucket artifacts only.
There is no publication parameter. Sources and CI are versioned
together. The pipeline builds directly in the Bitbucket checkout. `Prepare-Source`
initializes its submodules and records the commit, rejecting uncommitted changes
and stale build outputs before any build patches are applied. The build modifies
this disposable checkout; use a fresh checkout for each run. The `GITHUB_REVISION`
variable must not be set.
Build and signing remain active on all branches; GitHub and SMB preflight checks run only on `master`.

The deliverables are the x64 client and self-extracting EXE, not the MSI/templates,
ARM64, Sciter or other platforms covered by the cross-platform workflow.

patch applicability is checked before compilation.

## Build Tools 2026 (18.x)

Visual Studio 2022 is not required. `MSBUILD_PATH` must point to the **18.x**
instance, for example:
`C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\MSBuild\Current\Bin\MSBuild.exe`.
Preflight checks **v143 and v142** compiler files, x64 headers/libraries and
**CMake 4.2+** with the VS2026 generator. Compiler files alone are insufficient:
each toolset also needs its x64 MSBuild `Toolset.props` / `Toolset.targets` and
common C++ imports. CI searches `MSBuild/Microsoft/VC/v180`, then `v170`, then
`v160` **inside the selected VS2026 installation**, independently for v143/v142.
It selects the first complete integration. If v143 integration is absent while the
compiler is installed, `Test-Runner` restores four official Microsoft MSBuild v170
packages (17.14.36109.1, under 1 MB compressed), locked by URL and SHA256 in
`msbuild-tools.json`, into `work/msbuild-integration/<lock hash>`. Only the integration
tree is extracted; a SHA256 inventory is checked on reuse. v142 still uses its installed
integration. Nothing is copied into Visual Studio and no additional VS installation
or compiler is installed. CMake receives the actual VS2026 installation root explicitly,
so private targets resolve the existing compiler rather than a workspace-relative path.

CI initializes VsDevCmd with the selected exact v143 version; Rust and vcpkg use
that instance and compiler. A triplet overlay preserves static CRT linkage and
selects v143 for vcpkg. WindowInjection explicitly receives v142 and its version
through MSBuild, even though the main process environment uses v143. CMake receives
`VCTargetsPath=<validated path>` within `-T`, and WindowInjection receives the
corresponding `/p:VCTargetsPath=...`. This avoids MSB8020 when `v180` has no v143/v142
integration but older schema directories in the same installation do.

The libvpx overlay invokes MSBuild directly, bypassing CMake's toolset options.
`patches/libvpx-msbuild.patch` supplies the validated `VCTargetsPath`, actual
`VSInstallDir` and exact `VCToolsVersion` to that invocation. A separate
`build-tools/msbuild-selection.cmake` keeps the existing common triplet unchanged,
so this fix does not invalidate unrelated native-library cache entries.
Before the expensive dependency builds, `Test-Toolchain` also compiles and runs
a direct MSBuild probe with the same options as libvpx, in addition to both CMake
probes. The selection file and patch are included in diagnostics.

The Opus 1.5.2 port defaults to a dynamic CRT despite the static triplet.
`patches/opus-static-runtime.patch` explicitly enables `OPUS_STATIC_RUNTIME`.
After vcpkg installation, `dumpbin /directives` must report `LIBCMT` for Release
and `LIBCMTD` for Debug, without a dynamic CRT; otherwise the build stops before
the client. This invalidates only the Opus cache, leaving the common triplet unchanged.

Bridge generation also passes the full `libclang.dll` path through
`flutter_rust_bridge_codegen --llvm-path`: ffigen does not read `LIBCLANG_PATH`
or automatically search the LLVM directory inside Build Tools 2026.
The variable remains configured on Windows and is explicitly reused by CI.

All CI scripts are non-interactive and never request UAC elevation. Required
privileges must already be available in the runner service token before it starts.
A missing prerequisite causes an explicit preflight failure.

`patches/flutter-vs2026.patch` modifies only the private Flutter SDK: matching
instance selection, VS2026 generator, v143 toolset and checked CMake executable.
It is applied **before the first Flutter invocation**, so the tool snapshot
includes the fix. The patch, triplet and selected configuration are archived.
Internal variables `PROVDESK_VS_ROOT`, `PROVDESK_MSVC_VERSION` and
`PROVDESK_CMAKE_PATH`, `PROVDESK_CMAKE_TOOLSET` and `PROVDESK_VS_GLOBALS` are computed; do not configure them
in Bitbucket. `PROVDESK_CMAKE_TOOLSET` contains the complete v143 CMake toolset selection.

A .NET SDK alone is not sufficient. WDK and WiX/NuGet MSI tooling are not required
for this EXE delivery. The runner has 8 vCPUs and 8 GiB RAM, one active pipeline
and the Windows-managed page file. Stage order and pipeline concurrency remain
unchanged (timeout: 240 minutes).

Internal parallelism uses native scheduling without a script-imposed numeric cap
or overwriting operator-provided environment variables:

| Tool | Automatic behavior | Optional explicit limit |
|---|---|---|
| Cargo | Logical processor count, subject to native Cargo configuration | `CARGO_BUILD_JOBS` or Cargo `build.jobs` configuration |
| vcpkg | vcpkg-selected concurrency for underlying build systems (logical processors + 1 according to its documentation) | `VCPKG_MAX_CONCURRENCY` |
| Flutter / CMake Visual Studio | `--parallel` without a number, using the generator's native default | `CMAKE_BUILD_PARALLEL_LEVEL`, a positive integer |
| Direct MSBuild (WindowInjection and probes) | `/m` without a number | `CMAKE_BUILD_PARALLEL_LEVEL`, explicitly forwarded as `/m:N` and `MultiProcMaxCount=N` |

Mapping `CMAKE_BUILD_PARALLEL_LEVEL` to direct MSBuild is a convention of these
scripts, not a native MSBuild environment variable. Flutter lets CMake read an
explicit value and forwards that limit to the C++ scheduler as well. When unset
or empty, no computed or fixed numeric value is injected. Cargo and vcpkg retain
independent limits; the CMake variable does not cap them. Explicit MSVC settings,
including `CL_MPCount`, are not removed or rewritten; an explicit CMake limit
takes precedence for `MultiProcMaxCount` in the MSBuild calls we control.

MSBuild enables `UseMultiToolTask=true` and `EnforceProcessCountAcrossBuilds=true`
to coordinate C++ compiler processes across projects instead of multiplying `/m`
by `/MP`. Without a limit, MSVC chooses its concurrency. This does not cap Cargo
or every helper process. The vcpkg helper retains its native dynamic
`/m:${VCPKG_CONCURRENCY}`, `-maxCpuCount:${VCPKG_CONCURRENCY}` and
`MultiProcMaxCount=${VCPKG_CONCURRENCY}` options; these are not fixed at 2.
The libyuv port's `DISABLE_PARALLEL_CONFIGURE` is retained: it serializes CMake
Debug/Release configuration, not compilation jobs.

Automatic scheduling is primarily CPU-based, not available-memory-based. On the
8 GiB runner, concurrent Release/LTO jobs can exhaust memory, page heavily or fail;
running only one pipeline does not prevent this. No adaptive memory cap is added.
Operators can set the variables above if necessary. Rust Release, LTO and
codegen-units settings are unchanged. Free-disk checks do not check memory.

`Set-FlutterVs2026Patch` applies the maintained patch and can update a patched local
SDK from its receipt. It rejects unrecognized changes, restores the previous patch
if the replacement cannot apply, and invalidates only the stale flutter_tools
snapshot/stamp. The next authorized Flutter invocation rebuilds it; synchronization
alone does not invoke a compiler.

Tests without compilation cover automatic arguments, explicit limits and their
preservation, and SDK patch updates. Measure memory consumption on the runner
to adjust explicit limits to its capacity.

`MIN_FREE_DISK_GB` is an optional Bitbucket variable: a positive integer, defaulting
to **10 GiB**. Checks cover local volumes for the checkout, TEMP, profile and
Cargo/Rustup/LocalAppData caches before each script, before large installations
and before the final archive. Paths must use local drive letters (no UNC shares
or redirection to another volume). Below the threshold the pipeline stops without
deleting files. These are checkpoints, not disk reservations or a guarantee that
the full build will fit. Measure complete-build disk usage to size the runner.

## Execution and verification

```powershell
powershell -NoProfile -File ci/Test-Runner.ps1
```

On `master`, preflight checks GitHub access and the source commit, then tests SMB
access using temporary files. On all branches it may download the pinned
private MSBuild integration; it does not
compile, sign or use the private key. It checks tools,
configuration and discoverable VS components; it cannot replace a build to validate
private-key access, every SDK component or network access.

Order: `Test-Runner` → `Test-Ci` → `Prepare-Source` → `Test-Toolchain` → `Prepare-BuildEnvironment` → `Build-Payload`
→ `Complete-Payload` → `Sign-Payload` → `Package-Installer` → `Sign-Installer` → `Publish-GitHubRelease` → `Publish-Installer`.
The two publication stages run only on `master`.
One Bitbucket step keeps the same Windows host and key access. A clean checkout
is required; stale output is never reused.

Signing policy: unsigned EXE/DLL → WanPulse framework; valid third-party signatures
→ byte-for-byte preservation; invalid existing signatures → failure. A core ProVDesk
binary signed by another publisher is rejected. Driver packages are preserved and
verified against their catalogs (`/kp /c`), including declared INF/DLL/data files.
Third-party signatures are not timestamped again.

Before and after final signing, `Verify-Package.py` decompresses `data.bin`, compares
every file with the signed manifest and checks that the blob is embedded in the
EXE. Manifests, reports, patches, lockfiles, signed payload ZIP and final EXE go to `out/`.

### GitHub release publication (master only)

Pushes to `master` automatically build, sign and publish. Manual runs on `master`
also publish; all other branches retain Bitbucket artifacts only. There is no
publication variable. Both publication stages run after final signature verification.

Install the official GitHub CLI (`gh`) on the Windows runner PATH. Authentication
uses an organization-owned GitHub App with **Contents: write**, installed only on
the release repository. OpenSSL at `<Git installation>/usr/bin/openssl.exe` signs
the App JWT under Windows PowerShell 5.1; no additional PowerShell module is required.

Configure these Bitbucket **repository variables**:

| Name | Value | Secured |
| --- | --- | --- |
| `GITHUB_APP_CLIENT_ID` | Client ID from the App settings (not a client secret) | No |
| `GITHUB_APP_PRIVATE_KEY_BASE64` | Base64 encoding of the complete downloaded PEM private key | Yes |
| `GITHUB_RELEASE_REPOSITORY` | `wanpulse-sas/provdesk` (default) | No |

Do not configure a personal `GH_TOKEN` or run `gh auth login` on the runner.
On `master`, CI discovers the App installation for the target repository and
requests a token restricted to that repository and `contents:write`. A temporary
`GH_TOKEN` is used for preflight, then a fresh token for publication: installation
tokens expire after one hour, and builds can take longer. Each session attempts
to revoke its token in `finally` and restores the prior environment. Other branches
do not authenticate or request installation tokens. Offline tests use synthetic keys.
The private key is decoded into a temporary directory outside the checkout, with
inheritance disabled and access granted only to the current Windows account before
the key is written. The directory is removed in `finally`; forced process termination
can leave it behind. Keys and tokens must never be added to artifacts or logs.

Create the App under **wanpulse-sas → Settings → Developer settings → GitHub Apps**.
Disable webhooks, leave callback/setup URLs empty and do not request user OAuth
authorization. Grant only **Contents: read and write** (Metadata read is automatic),
and allow installation only on this organization. Generate a private key and install
the App on the intended fork. The installation ID is discovered automatically.
To copy a single-line key value without printing it in PowerShell:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\secure\app.private-key.pem')) | Set-Clipboard
```

Paste it into the secured Bitbucket variable, then clear the clipboard with
`Set-Clipboard -Value ''`. Keep the original PEM in your secret store.
The runner needs access to `api.github.com`, `uploads.github.com` and GitHub asset hosts.
On master, preflight checks GitHub access and requires its master commit to match
`BITBUCKET_COMMIT`. It obtains a Contents-write token but does not test a release upload. The same
commit check runs again before publishing; a newer GitHub master blocks an older build.

`Publish-GitHubRelease.ps1` reuses the existing WanPulse signature checks, verifies
the installer version, SHA-256 and current build manifest, and creates a tag
`provdesk-<version>-build.<Bitbucket build number>` at the exact built commit.
A draft release receives only:

- `ProVDesk-<version>-windows-x86_64.exe`: the same signed bytes as `out/ProVDesk.exe`;
- its `.sha256` file, referring to the versioned asset name;
- `build.json`: build and signature provenance.

Release notes include a Windows x64 download table, ProVDesk characteristics,
the product version, build number, source link and installer hash. GitHub also
provides source archives for the tag; submodules still require a recursive clone.
The draft is published only after the uploaded asset hashes have been checked.
Existing tags and releases are never overwritten. A failed attempt can leave a
reserved tag or draft: inspect and resolve it before retrying; there is no automatic cleanup.
GitHub publication precedes SMB publication. These services are not transactional:
a later SMB failure fails the pipeline but leaves the GitHub release published.
Payload archives, signature reports and diagnostics remain Bitbucket artifacts.

### SMB publication

On `master`, after GitHub release publication, `Publish-Installer.ps1` publishes only `out/ProVDesk.exe`
to `\\<ARTIFACTS_SHARING_HOST>\builds\WanPulse\ProVDesk\ProVDesk-<version>.exe`. The server comes from
required `ARTIFACTS_SHARING_HOST` (for example `wp-cloudstorage`, without a UNC
prefix or path). The `builds` share and `WanPulse\ProVDesk` subdirectory remain
fixed; `WANPULSE_OEM_PUBLISHER` does not change them.
The version is read from the signed final EXE's `ProductVersion`, recorded in
`build.json` and checked again before publication. Example: `ProVDesk-1.5.0.exe`.
Missing, inconsistent or unsafe filename versions block publication. Each successful
master build replaces only the file for that version; other versioned
executables are preserved in the same directory.

Required Bitbucket variables on `master`:

| Variable | Value | Secured |
|---|---|---|
| `ARTIFACTS_SHARING_HOST` | Server name, for example `wp-cloudstorage` | No |
| `ARTIFACTS_SHARING_USER` | Local account, `DOMAIN\account` or UPN | Optional |
| `ARTIFACTS_SHARING_PASSWORD` | Account password | Yes |

An unqualified account becomes `<ARTIFACTS_SHARING_HOST>\<account>`;
a `DOMAIN\account` or UPN is preserved. On `master`, at the start of `Test-Runner`, before
any downloads or compilation, preflight mounts the share using those credentials
and checks `WanPulse\ProVDesk`: directory creation if needed, writing, reading,
renaming with replacement, and deletion. It uses only two uniquely named
`.provdesk-preflight-<GUID>-*.tmp` files, cleans them up and removes the temporary
drive. Existing executables are never touched. Configuration, connection,
authentication or permission failures stop the pipeline before building and report
the failed operation. A network interruption can prevent cleanup; the unique names
identify any remaining probe files.

The runner needs name resolution for the configured server, SMB connectivity
(TCP 445), and the required folder permissions. Preflight checks access at that
moment; it does not guarantee availability until publication. No interactive
prompt or UAC elevation is required.

Publication requires the current Bitbucket build manifest, a valid timestamped
WanPulse signature, and a SHA256 matching `build.json`. The EXE is uploaded under
a unique temporary name, read back to verify its SHA256, then renamed to
`ProVDesk-<version>.exe`. The local `out/ProVDesk.exe` stays unchanged. Errors fail the pipeline; the temporary file is cleaned up when
possible and the SMB drive is removed. A network interruption can prevent cleanup.
No other `out/` files are copied. Outside `master`, this stage and the SMB preflight
are skipped; no SMB credentials are required.

Keep these as Bitbucket artifacts:

- `ProVDesk.exe.sha256`: final executable hash after signing.
- `build.json`: final EXE version, commits, build number, signer identity and final hash.
- `signatures.json`, `payload-signed.json`: signature report and embedded file
  inventory with hashes.
- `payload-signed.zip` and its SHA256: unpacked payload for analysis/support;
  this archive does not replace the distribution executable.
- Patches, version inventories and preflight logs: technical traceability.

The temporary PowerShell drive establishes the authenticated SMB connection.
File operations then use absolute UNC paths, not `ProVDeskPreflight...:\` or
`ProVDeskPublish...:\`: Windows PowerShell 5.1 can repeat the UNC root when
content operations use these virtual drives. Both preflight and publication
therefore use absolute UNC paths.

`Test-Publication.ps1` covers failure cases with local fixtures.
`Test-PublicationUnc.ps1` is an explicit integration test over **real SMB**. It
creates a unique subdirectory in the test share, runs preflight, checks file
publication and replacement, then removes its subtree and temporary drives.
No filesystem or drive commands are mocked; only the fake EXE's signing policy
is substituted. Use a dedicated test share, never the product output folder:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ci/tests/Test-PublicationUnc.ps1 -TestShareRoot '\\test-server\test-share'
```

The current Windows identity is used by default; `-TestCredential` accepts a
`PSCredential` when invoked within a PowerShell session. Run this test with
the identity and share permissions to verify. A local test does not validate the
Bitbucket account access to the publication server.


Driver packages are bundled only; they are never installed on the runner.

## Delivery validation

Run `provdesk-build-sign-package` on a branch other than `master` to validate
building and signing without GitHub or SMB publication. Download the artifacts, compare the EXE SHA-256 against `build.json`,
and verify its signature and timestamp. The manifest must identify the source
commit of the executed pipeline. Signature reports and the payload manifest
describe the files actually delivered.

Before merging to `master`, validate installation, upgrades, uninstallation,
remote access, display, printing and Defender in a VM using the signed branch artifact. Publish matching sources and patches with each
release; the SMB transfer publishes only the signed executable.

Signing is mandatory: inherited workspace `SKIP_SIGNATURE` is forced to `false` in this pipeline. Signing credentials remain required.

The pipeline maps a free SUBST drive (Z: through D:) to the existing checkout,
then runs all scripts through the short path. Files stay in place with their
existing ACLs, and artifacts remain under the checkout's `out/` directory.
A `finally` block removes the drive, including on failure; `after-script` retries
cleanup using the local `.ci-subst.json` ownership record. Cleanup checks the
target and refuses to remove a drive mapped elsewhere. Abrupt service or Windows
termination can prevent both cleanup paths; inspect SUBST mappings in the runner
context if that happens.

The triplet resolves includes through `CMAKE_CURRENT_LIST_DIR`. The validated exact
v143 version and VS2026 path are written to `build-tools/vcpkg-selection.cmake`
and archived. They do not depend on environment variables cleared by vcpkg.
A `cmake -P` triplet check validates includes before installation.

## Audit checks and diagnostics

`Test-Ci.ps1` runs fast tests before cloning and expensive compilation: signing policy,
native stderr/exit handling, driver catalogs, resources, VS2026 selection, Rust cache,
diagnostic collection, the vcpkg triplet and MSBuild options containing paths with
spaces. Each runs in a separate PowerShell 5.1
process. Python packaging tests run after installing Brotli. SUBST lifecycle tests
remain available separately for local validation, avoiding nested drive mappings in CI.

Signing stderr alone does not fail the pipeline. Nonzero exit codes remain fatal;
exit zero must be followed by valid Authenticode, the expected signer and a timestamp.
Raw framework output is never exported. Driver exemptions apply only to verified
catalog members; unexpected files in driver directories fail the pipeline.

Flutter receives `-T v143,host=x64,version=<validated version>,VCTargetsPath=<validated path>`, matching the exact
Rust/vcpkg compiler selection even with multiple v143 installations. `vcpkg list`
uses the installation's `--x-install-root` and requires the seven main native
libraries before archiving its inventory.

`diagnostics/**` is separate from `out/**`. Collection runs in `finally` before drive
removal, with an `after-script` fallback. Allowed files are `.log` files under vcpkg
buildtrees and the Flutter Windows build, plus explicit inventory/configuration files.
Limits: 5 MiB per file and 50 MiB total before redaction; skipped files are listed in
`index.txt`. Values from PASSWORD/SECRET/TOKEN/SIGNING_CONTAINER environment variables
and HTTP URL userinfo are redacted. Unknown or transformed secrets may escape this
filter: keep artifacts private. Abrupt termination may prevent collection. Signed
deliverables are exposed under `out/**` only after success.

## Rust utility cache

The persistent per-runner-account cache lives at
`%LOCALAPPDATA%/WanPulse/ProVDesk/ci-tools/<key>`. Its key includes `ci/rust-tools.json`
(versions, features, target and Rust), the exact MSVC version and cache implementation.
Only cargo-expand and flutter_rust_bridge_codegen are reused, never application payloads,
signatures or secrets. Every use checks the stored SHA256, executable version and copy
integrity in `build-tools/rust/bin`. Missing or corrupted entries trigger a `--locked`
reinstall. An exclusive lock prevents concurrent updates of the same entry.

Entries are saved after each installed utility, even if the later build fails. Old
keys are not automatically deleted: monitor disk usage and remove unused entries
when no CI is running. Disk checks already include the LOCALAPPDATA volume. Cache
hashes do not protect against malicious changes by the runner account itself;
restrict access to that account and administrators.

`Test-PipelineLifecycle.ps1` locally exercises the runner and cleanup with stub stages, on success and failure, without compiling or signing.

The generated VS2026 path preserves the exact Windows separators and casing returned by vswhere: vcpkg compares the selection path against the detected instance. CMake bracket arguments preserve backslashes.

## Tool interactions checked before compilation

After source checkout, `Test-Toolchain.ps1` checks patch applicability and actually
loads libclang and verifies directory symlink creation for Flutter. It first runs
the native compiler probes described below, before
downloading vcpkg or its helper tools. It then prepares vcpkg and invokes
**`vcpkg env`** with the real triplet and install root, checking the resolved compiler
and VCToolsVersion inside that isolated environment. This happens before Flutter
and Rust utility setup.

Two small CMake projects exercise C++ compilation, Windows resources, linking and
execution with v143 and v142, using the same explicit MSBuild targets selection as
the application. A compile-time assertion rejects a different MSVC minor version.
A third probe invokes MSBuild directly with the properties supplied to the libvpx port.
The CMake v143 probe is signed and timestamped by the WanPulse
framework and verified: this uses the runner key before the application build.
Probe executables are removed and are not deliverables. Non-secret logs and results
are added to diagnostics.

`Test-SigningPipeline.ps1` executes the actual Sign-Payload script with multiple files,
fake native tools and mocked cryptography. It checks JSON manifests, the report and
vendor-byte preservation. JSON arrays are explicitly unwrapped for PowerShell 5.1.
`Test-ForkPackage.py` invokes the exact fork Python generator with Brotli 1.2.1 and
checks nested files, accents, empty content and the entrypoint. It does not compile
the wrapper or validate its Windows runtime behavior.

Local tests do not replace a complete signed pipeline run. Validate
installation, upgrades, remote sessions, uninstallation and Defender
detections in a VM using the signed installer.

## Repositories and runner

GitHub hosts the sources and CI. Bitbucket runs the same Git commit on a Windows
runner with the `self.hosted`, `windows`, `capability.build` and `capability.sign`
labels. Signing and publication settings come from Bitbucket variables and the
runner configuration; secrets are not committed. Check that both repositories
point to the same commit before starting a pipeline. GitHub Actions workflows
are not required for this build process.

## Push a branch to GitHub and Bitbucket

A single local clone is sufficient. Configure a `publish` remote with two push
destinations, replacing the example URLs with the repository URLs:

```powershell
git remote add publish <GITHUB_URL>
git remote set-url --add --push publish <GITHUB_URL>
git remote set-url --add --push publish <BITBUCKET_URL>
```

After editing and committing, `git push publish HEAD` sends the current branch
to both repositories. To restrict `git push publish` to a specific branch, set
`remote.publish.push` to `refs/heads/<branch>:refs/heads/<branch>`.
This configuration is local to the clone and requires write access to both
services. The two pushes are not atomic: after a partial failure, compare SHAs
with `git ls-remote <URL> refs/heads/<branch>` and complete the missing push
without forcing a divergence. Fetch changes made directly on either website
before pushing.
For `master`, push to GitHub first, then Bitbucket: the Bitbucket push automatically
starts building and publishing, and GitHub master must already match the built commit.
